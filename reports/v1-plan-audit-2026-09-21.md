# V1 plan audit and execution recommendation

Reviewed 21 September 2026. Advisory report: recommendations below are not adopted design decisions and do not authorise application implementation. Sources are the current plans 00–06 and 08, HANDOFF, the README, existing review reports, and targeted source inspection. Plans 07 and 09 do not yet exist.

The direction is coherent: a Swedish passenger railway management game with a strong timetable-planning interface. The existing construction editor is a useful foundation. The plans are ready to guide the remaining design discussions, but they are not yet an executable specification. Their weakest area is interaction between subsystems, especially durable state, runtime transitions, and performance.

Keep the current React/TypeScript/MapLibre application. Introduce a headless simulation core behind the planned worker boundary, then deliver small playable increments across the subsystems. Do not implement the documents in numerical order or attempt the complete national simulation in one pass.

## Findings to resolve before the affected implementation

| Priority | Evidence | Consequence and recommended resolution |
| --- | --- | --- |
| Blocking | [08: saves and live-state exception](../plans/v1/08-simulation-architecture-and-saves.md) saves authored state plus clock, running trips and positions, while 04 requires servicing mileage, 05 requires reliability memory, and 06 requires transaction history and compliance. | These facts cannot all be reconstructed from current infrastructure and balance. Separate authored definitions, durable runtime/history, and disposable caches. Explicitly persist or reconstruct speed/motion phase, occupancy/reservation state, active timetable versions, servicing progress, mileage, ledger/weekly aggregates, contract progress, reliability records and random-generator state. Define reconstruction invariants instead of assuming everything non-authored is derivable. |
| Blocking | 08 resamples passengers and says the discontinuity is confined to passengers; 02 makes dwell depend on passenger exchange, and 06 earns fares from journeys. | Passenger resets can change train timing, capacity and future revenue. Specify how onboard loads, outstanding journeys and recognised revenue survive reload. Either widen the live-state exception or explicitly accept and test a broader discontinuity. Loading the same checkpoint twice deterministically is different from matching an uninterrupted run. |
| Blocking | 08 snapshots all authored state for undo, including balance, fleet and published timetables, while live operation continues separately. | Restoring an old balance can erase earned revenue; restoring infrastructure can strand a current train. Recommended first rule: committed edits are undoable only within a paused editing session; clear the stack on resume, load and publication. Apply cost changes atomically with infrastructure/fleet changes and recheck invariants on undo. Revisit broader undo later. |
| Blocking | [02: deadlock prevention](../plans/v1/02-infrastructure-and-operations.md) promises impossibility but leaves reservation scope, release, safe holding locations and station/loop interaction open. | The guarantee is not established by the prose. Specify an operational graph, whole-train clearance, atomic resource acquisition, deterministic priority and release rules. Test cyclic waits involving multiple loops/stations and planned meets with cancelled or blocked counterparts. Collision avoidance, deadlock freedom and eventual progress need separate acceptance checks. |
| Blocking | [03: activation](../plans/v1/03-services-and-timetabling.md) keeps old running trips while all future departures use the new week; 04 assigns physical units across duties. | A new duty can demand a unit still running an old trip. Retiming can also cause duplicate departures. Give each actual trip a timetable-version/week-occurrence identity, preserve active old definitions, and validate publication against live train positions and commitments. Define skipped/past departures and old/new meet references. |
| Blocking | 05 and 08 allow weighted passengers but require hard capacity and claim weights keep totals correct. | A traveller representing 20 people cannot simply board a train with three seats left. Specify partial boarding/splitting or another bounded conservation rule, queue ordering, weighted fares and weighted dwell. Sampling preserves expectations under suitable rules, not exact nonlinear outcomes automatically. Sampling must not depend on camera position or machine speed if deterministic outcomes are required. |
| High | 05 costs itineraries using the technical minimum; 03 permits longer authored allowances. | Passengers must use published arrival/departure times, including allowance, dwell and transfer feasibility. The shared movement model supplies physical minima and operational predictions; it does not replace the published timetable with an optimistic minimum. Define forecast inputs and iteration for crowding-dependent dwell. |
| High | 05 says agents already exist only for plausibly served journeys, then proposes aggregate flows outside the served area as its fallback; 08 repeats that fallback. | The fallback does little if those outside agents never existed. Budget served-area routing and agents explicitly. Measure candidate-search caching, shared searches by OD/time band, cohort sampling, bounded replanning and forecast frequency before changing the model. |
| High | 08 gives per-step and fast-forward targets without a step size or benchmark hardware; one worker also performs full-week validation. | Targets cannot yet establish feasibility. At a 1-second step, 60× needs 60 steps per wall-second: less than 16.7 ms each before other work; a 25 ms ceiling does not guarantee it. A 15-second synchronous validation would also stop that worker's simulation and command handling. Use cancellable, bounded work slices over versioned immutable inputs; ignore stale results. Specify hardware/browser, workload, p95 latency, memory and total throughput. |
| High | 06 bounds borrowing by recent revenue, blocks borrowing on insolvency, and assumes operations can recover the balance. | Zero-revenue startup and a structurally loss-making network can become traps. Set scenario capital/initial credit explicitly, define negative-balance and debt-payment behaviour, and demonstrate a recovery path using allowed actions. Define contract tolerances and payment timing so loans and subsidy close the initial loop. |
| High | 04 blocks a servicedue train's next departure, including an apparent need to travel to a depot. | Specify whether a servicing-only empty movement is allowed, or ensure preventive servicing before the threshold. Test a train becoming due at a station away from its depot. Also settle whether a siding holds one train or multiple trains by total usable length: the document's pool wording and two-train acceptance example do not establish the same capacity rule. |
| High | 08's final paragraph requires proving national performance before implementation readiness. | This creates a planning loop: evidence requires code. After design blockers close, authorise bounded feasibility implementations with explicit exit criteria. Keep national performance an expansion/release gate, with an early synthetic scale probe, rather than requiring proof before the first simulation exists. |

## Smaller consistency repairs

- In 03, whole-trip detachment and publication of structurally invalid trips are described as settled and also left open. Choose one rule for each and update the acceptance scenarios.
- In 04, references to trains “failing” short platforms and length assignment checks must consistently mean additional dwell, not rejection. Its own acceptance table already says this correctly.
- In 05, “one agent is one person” needs reconciling with 08's weighted representation. Distinguish unserved travel opportunity from published-timetable forecast: the plan currently says forecast needs service and also places demand between wholly unserved places in that layer.
- 03's closing paragraph still lists validation cost as unresolved after 08 resolves the tiering approach. Some roadmap/status references are similarly stale.
- 06's phrase “a player cannot be made insolvent by a running train” conflicts with ongoing costs exhausting the balance. The apparent intended rule is that insolvency does not interrupt an underway trip.
- 08 overstates two implementation properties: immutable snapshots retain memory even when references are cheap, and localStorage errors can be caught. IndexedDB is a sensible choice but does not guarantee that a large save succeeds.

The current source still contains the documented silent station-discard path in `src/persistence.ts`, section-speed-only `coveredJourney` in `src/planning.ts`, and React-owned project state in `src/App.tsx`. These are confirmed foundations/debts, not newly implemented fixes. Preserve useful construction, geometry and catchment code behind adapters while replacing its authority over simulation state.

## Finish planning with a small implementation contract

Complete 07 around one usable journey: build/select a corridor, author a pattern, generate trips, assign duties, publish, run, diagnose, improve. My proposed interface is a map workspace with task panels, a table as the precise timetable editor, and a linked time-distance diagram for analysis. Test the workflow with a simple prototype before designing every national overlay. Make pending checks, blocked departures and proposed assistance distinct.

Resolve the blocking rows above in their owning plans. Record each decision once, including its affected acceptance cases. Avoid expanding this into another broad design document.

Complete 09 as a scope contract: first-playable requirements, later v1 requirements, and post-v1 exclusions. Each requirement needs an observable pass condition, prerequisite and fixture. A subsystem's completion is not a milestone unless the user can exercise its effect.

Freeze only the contracts needed for the next milestone: identifiers and units; simulation time/week occurrence; construction-to-operational-graph conversion; command acknowledgement and revision rules; error taxonomy; authored/durable/derived state ownership; save schema; and the first fixture. Keep train, demand and economic constants in versioned tuning data. Source evidence and gameplay adjustments should be separate fields. Do not wait for perfect nationwide calibration before testing the corridor.

The first playable should retain the proposed four-station corridor, regional and express services, a single-track bottleneck and passing location, one depot and two types. Use only enough physical trains for the duties; the plan's ten-train figure can remain a separate stress fixture. Design the calls to make at least one transfer useful: two overlapping end-to-end services do not automatically demonstrate transfers. Include a depot visit and one manageable contract. All later v1 commitments stay in the backlog rather than being silently dropped.

Keep three fixtures: a tiny synthetic graph for precise invariants, a curated Swedish corridor for real map integration and playtesting, and generated regional/national workloads for scale. Real geography alone is a poor diagnostic fixture.

## Implementation discipline and release gates

Use a pure TypeScript domain core with no React, DOM or MapLibre dependencies. Run that same core in headless tests and in the browser worker. Keep one movement/resource implementation, but give prediction isolated state so validating a draft cannot mutate the running railway. Use revision-tagged commands/results, explicit rejection reasons, and atomic mutations. Render only subscribed information; a corridor diagram and national inventory need subscriptions beyond the map viewport.

Keep one implementation task focused on one demonstrated behaviour, with its acceptance cases and explicit exclusions attached. Integrate continuously through small reviewed changes. Introduce minimal UI with each behaviour so usability failures appear early. Avoid a full rewrite of App.tsx before proving a train can run, and avoid duplicating game rules in UI code while extracting it.

Test domain invariants (separation, reservations, capacity, unit identity, money conservation), deterministic runs, checkpoint consistency, command/publication transitions and weekly boundaries. Use browser tests for the complete build-to-operate workflow. Benchmark on a named reference environment; use repeated/p95 measurements rather than fragile single-run timing assertions on arbitrary developer machines. No hardware-independent national speed claim is justified yet.

Browser delivery fits the current repository and no-server scope. Worker messages support the planned separation; they do not make long computations inside the worker preemptible. See [MDN's worker documentation](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers). Keep desktop packaging as a later distribution decision, after the playable and measured performance establish the need.

IndexedDB remains subject to quota errors and browser eviction. Add failed-write handling, recovery slots and file export; consider persistent-storage requests. Export is the player's independent backup. See [MDN's storage quotas and eviction documentation](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

Before a public v1, explicitly agree supported desktop browsers, minimum hardware, expected data download size, save compatibility policy and data snapshot identity. Pin a tested dataset per release and test the built application against it. The runtime should not require a successful fresh national download to begin playing.

Calendar estimates should follow milestones 0–2: they expose the hardest operational and authoring risks. Plan by demonstrated exit gates until that evidence exists. The earliest useful success criterion is a player making one timetable or infrastructure change and understanding its effect on an operating railway.
